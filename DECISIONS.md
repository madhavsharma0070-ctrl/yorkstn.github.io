# Yorkstn — Decisions Log

Architecture/product decisions made across this build, in chronological order. Each entry states the decision, why, and where it's elaborated in full. This is the fast-reference index; the source documents (`docs/phase2/*.md`, `docs/phase3/*.md`) are authoritative for detail — if this log and a source document ever disagree, the source document wins and this log should be corrected.

---

## D-01 — Yorkstn is a technology-first Market Entry Operating System (SaaS + optional managed services)
**Decision:** Software platform is the primary product; managed services (legal/compliance execution, entity formation, strategic advisory, partner-onboarding diligence) are an optional paid layer, not a requirement to use the software.
**Why:** Approved directly by the user (2026-07-24) as the Phase 2 starting assumption, consistent with Phase 1's finding that pure self-service is likely insufficient for India's highest-stakes early compliance steps.
**See:** `docs/phase2/PRD.md` §1, §4.

## D-02 — MVP scope is exactly four modules, no fifth
**Decision:** AI Market Intelligence, Compliance Operating System, Partner Discovery Platform, Retail Expansion Intelligence — approved by the user as MVP scope; no additional module added.
**See:** `docs/phase2/PRD.md` §5.

## D-03 — RBAC modeled as a fixed enum, not a normalized permission graph
**Decision:** `memberships.role` is a Postgres enum (`owner`, `admin`, `compliance_manager`, `analyst_editor`, `viewer`), not a `roles`/`permissions`/`role_permissions` join graph. Yorkstn Staff and Partner are separate `user_type`s, never membership roles.
**Why:** The product has a fixed, product-wide role set in MVP — no tenant-customizable permissions exist yet. A migration path to a normalized graph is documented if that changes.
**See:** `docs/phase2/DATABASE_SCHEMA.md` §0.2, `docs/phase2/AUTH_RBAC.md`.

## D-04 — Deterministic features are structurally separated from generative AI output
**Decision:** Expansion Readiness Score and the Entity Formation recommendation are plain rules-engine computations, stored in their own tables (`expansion_readiness_scores`, `compliance_workflow_items.recommended_entity_type`) — never modeled as, or generated by, the `ai_insights` AI-output pipeline.
**Why:** These outputs carry real legal/decision consequence and must be reproducible and auditable (same inputs → same output, tested), which a generative model cannot guarantee.
**See:** `docs/phase2/FEATURE_SPECIFICATIONS.md` (AI Output Standard header), `docs/phase2/AI_ARCHITECTURE.md` (a/b/c/d feature categorization), `docs/phase2/DATABASE_SCHEMA.md` §1.3.

## D-05 — Every AI-generated output follows one standard shape (the "AI Output Standard")
**Decision:** `summary`, `confidence`, `sources[]`, `assumptions[]`, `generatedAt`, `modelVersion` on every generative feature's output, enforced by one shared `ai_insights` table/envelope rather than per-feature ad hoc shapes.
**Why:** Operationalizes Phase 1's "cite sources or explicitly label as assumption, never fabricate" research discipline as a product-level, code-enforced requirement, not just a documentation convention.
**See:** `docs/phase2/FEATURE_SPECIFICATIONS.md`, `docs/phase2/DATABASE_SCHEMA.md` §1.3.

## D-06 — Modular monolith, not microservices
**Decision:** Build the platform as one Next.js application with clean internal module boundaries, not independently deployed services.
**Why:** Small team, single Amplify build pipeline, no scale problem yet — microservices would be premature infrastructure investment before product-market fit. Extraction path is preserved for later if a specific module (e.g., Partner search indexing, AI worker fleet) genuinely outgrows the monolith.
**See:** `docs/phase2/SYSTEM_ARCHITECTURE.md` §1.

## D-07 — The new platform is added inside the existing repo/app, not a new repo or a separate deployment
**Decision:** The authenticated platform (`/app/**` platform routes, `/partner-portal/**`) is built inside the existing `yorkstn/` Next.js app, deployed by the same `amplify.yml`/Amplify build as the marketing site. The existing marketing site's custom CSS design system, copy, and pages are **not** touched, migrated, or refactored.
**Why:** `yorkstn.github.io` is explicitly the long-term Yorkstn codebase per the user's Phase 3 instruction ("audit the existing repo... evolve it... reuse existing components... without unnecessary rewrites"); the marketing site and the authenticated platform are different products with different design languages and should not be forced into one visual system.
**See:** `docs/phase2/DEPLOYMENT_ARCHITECTURE.md` §2, `docs/phase2/TECH_STACK.md` §2.

## D-08 — Tailwind CSS introduced, scoped only to the new platform routes
**Decision:** Add Tailwind for `app/app/**`, `app/partner-portal/**`, and `components/platform/**`. Existing marketing-site CSS is untouched.
**Why:** Building four data-dense enterprise modules by hand-rolling CSS (as the marketing site does) would be far slower than the marketing site's bespoke-aesthetic approach justifies for internal dashboards; Tailwind is scoped so the two design systems never collide.
**See:** `docs/phase2/TECH_STACK.md` §2.

## D-09 — Prisma + PostgreSQL (prod/staging) + SQLite (local dev)
**Decision:** Prisma is the sole ORM/data-access layer. Local development runs against SQLite (no cloud DB credentials exist in this environment); the Prisma schema is written to be Postgres-compatible so staging/production can point at real Postgres once provisioned.
**See:** `docs/phase2/TECH_STACK.md` §3–4, `docs/phase2/DEPLOYMENT_ARCHITECTURE.md` §5, §8.

## D-10 — NextAuth.js (Auth.js), Credentials provider + JWT sessions, for MVP auth
**Decision:** NextAuth.js with a Credentials provider (email/password) and JWT session strategy (not database sessions) is the MVP auth approach. The Prisma adapter's standard tables (`accounts`, `sessions`, `verification_tokens`) are defined for future OAuth support but unused by the credentials+JWT flow itself.
**See:** `docs/phase2/AUTH_RBAC.md` §1, `docs/phase2/TECH_STACK.md` §5.

## D-11 — AI service layer is provider-agnostic, defaults to a deterministic mock provider
**Decision:** All AI-generation features are built behind a swappable provider interface. The MVP default implementation is a deterministic **mock provider** producing AI-Output-Standard-shaped responses from seed/curated data — no real LLM API key is required for the MVP to be fully functional and demoable. Wiring a real provider (recommended: Anthropic Claude via `ANTHROPIC_API_KEY`) is a documented environment-variable swap, not a code change.
**Why:** No LLM API key is available/provisioned in this build environment. Per the project's "flag rather than fabricate access to infrastructure" rule, the system is built to work honestly without one, with the real integration point fully designed and ready.
**See:** `docs/phase2/AI_ARCHITECTURE.md`, `docs/phase2/MVP_ROADMAP.md` (Milestone 4), `docs/phase2/DEPLOYMENT_ARCHITECTURE.md` §8.

## D-12 — Deterministic/curated-lookup features are never delegated to an LLM
**Decision:** Category (b) features (e.g., BIS/QCO applicability by HSN code) are plain structured lookup tables maintained/versioned in the DB, never "ask the model to know this."
**Why:** These are facts with a definite correct answer that an LLM can hallucinate; a lookup table is both more correct and auditable.
**See:** `docs/phase2/AI_ARCHITECTURE.md`.

## D-13 — Documents table is polymorphic and application-enforced, not a DB-level FK
**Decision:** `documents.attached_to_id` references either a `compliance_workflow_items` row or a `partner_verifications`-linked partner, discriminated by `attached_to_type`, with no database foreign-key constraint across the two possible parents — enforced in application code instead.
**Why:** Lets one Document Management feature serve both Compliance and Partner-verification uploads without duplicating the table; the tradeoff (losing DB-level referential integrity on this one table) is deliberate and documented, not an oversight.
**See:** `docs/phase2/DATABASE_SCHEMA.md` §1.4, `docs/phase2/ERD.md` §3.

## D-14 — Partners and city/mall reference data are the only non-tenant-scoped, shared tables
**Decision:** Every other table carries `organization_id`. `partners` (a shared directory), `cities`/`malls` (shared reference content), and `users` (cross-tenant by design) are the explicit, documented exceptions to the tenant-isolation invariant.
**Why:** Tenant isolation is the single most important security invariant in the system (per `SECURITY_ARCHITECTURE.md`); documenting exceptions explicitly prevents them from being mistaken for a missed scoping bug later.
**See:** `docs/phase2/DATABASE_SCHEMA.md`, `docs/phase2/SECURITY_ARCHITECTURE.md`.

## D-15 — API versioned via URL prefix (`/api/v1`), not headers
**Decision:** Simple URL-prefix versioning, justified by having no external third-party API consumers in MVP (the API serves only the Yorkstn frontend).
**See:** `docs/phase2/API_SPECIFICATION.md` §0.

## D-16 — Build order: foundation → deterministic Compliance workflows → shared AI layer → generative Market Intelligence → Partner Discovery → aggregating Expansion Intelligence → Managed Services/hardening
**Decision:** 8 relative milestones (not calendar dates), sequenced strictly by dependency — Compliance OS ships before AI Market Intelligence specifically because it is lower AI-risk (deterministic) and unblocks the Readiness Score's real completion-percentage input.
**See:** `docs/phase2/MVP_ROADMAP.md`, `docs/phase2/MILESTONES.md`.

## D-21 — Tailwind pinned to v3 (not v4), prefixed `tw-`, preflight disabled
**Decision:** `tailwindcss` is pinned to `^3` (npm installed v4 by default, a CSS-first config paradigm change not assumed by `docs/phase2/TECH_STACK.md`). The v3 config sets `prefix: 'tw-'` and `corePlugins.preflight = false`, and `content` is scoped only to `app/app/**`, `app/partner-portal/**`, `components/platform/**`.
**Why:** `TECH_STACK.md` §2 says Tailwind should be "scoped to platform routes only," but Next.js App Router CSS is bundled per-route-segment, not truly style-scoped — a global stylesheet imported in a nested layout can still affect the whole app once client-side navigation loads it. Disabling preflight (Tailwind's global CSS reset) and prefixing every utility class removes the actual risk (global resets, class-name collisions with the marketing site's plain class names like `.btn`/`.nav`) regardless of Next.js's bundling behavior, rather than relying on bundling alone to keep the two design systems apart.
**See:** `yorkstn/tailwind.config.js`, `yorkstn/app/app/platform.css`.

## D-22 — Json fields are nullable, not `@default("{}")`/`@default("[]")`
**Decision:** Every `Json` column in `yorkstn/prisma/schema.prisma` (`assumptions`, `payload`, `capacityAttributes`, `demographics`, `realEstateCostBenchmark`, `distributionMaturity`, `tenantMix`, `leaseBenchmark`, `attributes`) is `Json?` (nullable, no default), not `Json @default("{}")`/`@default("[]")`.
**Why:** Prisma's SQLite migration generator emitted `DEFAULT {}` (an unquoted bare object) for these fields, which is invalid SQLite SQL and silently broke `prisma migrate dev` partway through table creation (discovered when only 12 of ~32 tables existed after a "successful"-looking migration run). Making the fields nullable sidesteps the broken default generation entirely; application code treats `null` as the empty/unknown case (`?? []`, `?? {}`) at the point of use instead of relying on a DB-level default.
**See:** `yorkstn/prisma/schema.prisma`, this repo's Prisma migration history (the corrected migration replaces an earlier broken one — see the commit that follows this decision).

## D-23 — Marketing site and platform use separate root layouts via Next.js route groups ("parallel root layouts")
**Decision:** The existing marketing site was moved (via `git mv`, no content changes) into `app/(marketing)/` with its existing `layout.tsx`/`globals.css` intact as that group's root layout. The new platform lives at `app/(platform)/app/**`, with its own root layout at `app/(platform)/app/layout.tsx` (its own `<html>/<body>`, own metadata, own CSS). There is no `layout.tsx` at the top level of `app/` — API routes (`app/api/**`) are unaffected since route handlers don't participate in the layout tree.
**Why:** A first attempt nested the platform's layout *under* the marketing site's existing root layout (`app/app/layout.tsx` as a child of `app/layout.tsx`). Because Next.js App Router wraps every route under `app/` in whatever root layout exists at the top, every platform page would have inherited the marketing site's `<Navbar>`, custom-cursor effects, and cookie banner — the exact cross-contamination D-07/D-08 were meant to prevent, just not caught until actually building the pages. Next.js's documented "multiple root layouts via route groups" pattern is the correct fix: two sibling route groups, each independently rooted, guarantee at the framework level (not just by convention) that the two design systems never share a page.
**Impact:** Marketing site URLs are unchanged (`/about`, `/contact`, etc. — route groups don't affect URLs). Platform URLs are `/app/**` as originally planned (the IA's "/app in MVP" note), reached via `app/(platform)/app/**/page.tsx`.
**See:** `yorkstn/app/(marketing)/layout.tsx`, `yorkstn/app/(platform)/app/layout.tsx`.

## D-24 — Corrected `Document`/`DocumentVersion` schema drift before building Document Management (Milestone 2)
**Decision:** Fixed `yorkstn/prisma/schema.prisma`'s `Document` and `DocumentVersion` models, and the `attachedToTypeSchema` Zod enum, to match `docs/phase2/DATABASE_SCHEMA.md` §1.4 exactly: `Document` gained `title` and `deletedAt` (soft-delete of the record) and lost the ad hoc `documentGroupId`/`uploadedByUserId` fields it had been given in Milestone 1's initial schema; `DocumentVersion` gained `checksum`, its own `uploadedByUserId`/`uploadedAt`, and renamed `fileUrl` → `storageKey` (an opaque key resolved by `lib/modules/compliance/documents/storage.adapter.ts`, not a public URL); `attachedToTypeSchema` widened from an ad hoc 2-value set to the documented 4-value set (`compliance_workflow_item`, `partner`, `brand_profile`, `managed_service_engagement`).
**Why:** Milestone 1's schema was written from a partial reading of the (very long) `DATABASE_SCHEMA.md`; building the actual Document Management feature in Milestone 2 required re-reading that section closely, which surfaced the drift. Fixed forward before any real document data existed (the tables were empty — verified before migrating) rather than carrying the inconsistency into Milestone 2's code.
**See:** migration `20260727122319_fix_document_versioning_schema`.

## D-17 — Three Phase 2 background research agents hit the account session-usage limit mid-run; their completed file writes were kept, only genuinely missing files were rewritten
**Decision:** On investigation, all three agents' file-write tool calls had already succeeded before the session-limit error interrupted their final summary step (verified by checking each file for a natural, non-truncated ending). Only the 5 files an agent had not yet reached (`ERD.md`, `API_SPECIFICATION.md`, `AUTH_RBAC.md`, `MILESTONES.md`, `VALIDATION_PLAN.md`) were written directly in the main session, matching the existing files' naming/table conventions exactly (verified by reading the completed `DATABASE_SCHEMA.md` first). No completed work was overwritten or duplicated.
**See:** commit `2c80da8`, this repo's git history.

## D-18 — Prisma schema implements DATABASE_SCHEMA.md's Postgres ENUMs as validated `String` fields
**Decision:** Every column DATABASE_SCHEMA.md models as a native Postgres `ENUM` (role, status, category fields across all modules) is a plain `String` in `yorkstn/prisma/schema.prisma`, with the closed value set enforced by Zod schemas at the API boundary (`lib/validation/enums.ts`) rather than by the database engine. Postgres `text[]` columns (e.g., `assumptions`) are `Json` for the same reason.
**Why:** Prisma's native `enum` type and array columns are unsupported on SQLite, our chosen local-dev provider (`docs/phase2/TECH_STACK.md` §4). This preserves the same closed-value-set guarantee — just enforced in the application layer, consistent with the Zod-at-the-boundary convention `docs/phase2/API_SPECIFICATION.md` §0.2 already established — and keeps one schema file working identically against SQLite (dev) and Postgres (staging/prod), which was the whole point of the SQLite/Postgres choice in the first place.
**See:** `yorkstn/prisma/schema.prisma` header comment, `yorkstn/lib/validation/enums.ts`.

## D-19 — Pinned to Prisma 6.x, not the newly-released Prisma 7
**Decision:** `prisma`/`@prisma/client` are pinned to `^6`, not the latest major (7), which was installed by default when this build began.
**Why:** Prisma 7 removed the classic `datasource { url = env(...) }` schema pattern in favor of a `prisma.config.ts` + driver-adapter model. All of Phase 2's architecture docs (`DATABASE_SCHEMA.md`, `TECH_STACK.md`, `DEPLOYMENT_ARCHITECTURE.md`) were written assuming the classic, still-widely-documented pattern; adopting Prisma 7's new config model would have been an unplanned, riskier architecture change made under time pressure rather than a deliberate one. Revisit this pin deliberately (not as a side effect of `npm update`) once Prisma 7's adapter model has matured and a real reason to upgrade exists.
**See:** `yorkstn/package.json`, this repo's Prisma migration history.

## D-20 — Document storage behind a provider interface, defaulting to local filesystem (dev), S3 documented as the production target
**Decision:** `lib/modules/compliance/documents/storage.adapter.ts` (per `docs/phase3/compliance-operating-system-engineering-spec.md` §1) exposes one interface with two implementations: a `local` adapter (writes to a gitignored `.local-storage/` directory, dev-only) and an `s3` adapter (inactive until AWS S3 credentials + bucket are provisioned, per `docs/phase2/DEPLOYMENT_ARCHITECTURE.md` §8). Selected via `DOCUMENT_STORAGE_PROVIDER` env var.
**Why:** No S3 bucket/credentials exist in this build environment; per the project's "flag rather than fabricate access to infrastructure" rule, Document Management must still work end-to-end for local development and demos without them.
**See:** `yorkstn/.env.local.example`.
